# Agent 评测的用户需求与价值验证

公开来源核查日期：2026-09-08。产品方向对齐日期：2026-09-16。
本文保留当时的公开需求证据，补充其与当前评测范围的关系；本次未重新核查外部来源，
不把方向更新当作新的市场调研，也不以开发实验结果证明产品需求。
当前优先级以[产品路线图](../../ROADMAP.zh-CN.md)为准。

**判断：评测产品无需亲自修改 Agent，仍然可以创造价值；但必须帮助用户完成有价值的决策或改善工作结果。** 可购买的结果包括更快定位并修复问题、更快安全采用新模型、减少回归，以及在质量不降的条件下降低成本。仅有严谨分数、完整证据或成功运行的批次，不足以证明用户需要另一个产品。

“不自动优化 Agent”与“不能帮助用户改善 Agent”有实质区别。下面的客户案例支持前者有价值；它们并不支持后者是有竞争力的定位。

## 已核查的四组需求证据

### 1. 开发者确实面对质量与调试负担，但这不等于评测采购意愿

[Stack Overflow 2025 Developer Survey — AI](https://survey.stackoverflow.co/2025/ai) 报告：66% 的回答者遇到“AI solutions that are almost right, but not quite”，45.2% 遇到“Debugging AI-generated code is more time-consuming”。准确性信任选项中，“somewhat/highly distrust”合计 45.7%，“somewhat/highly trust”合计 32.7%；正文分别四舍五入为 46% 与 33%。

这是一条独立于评测平台厂商的痛点证据：用户需要减少验证和调试负担，不能只增加一份需要人读懂的报告。但调查对象是广义开发者，不能把数字解释为 Agent 开发团队比例、Cernora 目标客户比例，或愿意付费购买评测产品的比例。

[官方方法说明](https://survey.stackoverflow.co/2025/methodology) 给出 49,009 份有效答卷、177 个国家，采集期为 2025-05-29 至 2025-06-23；主要经 Stack Overflow 自有渠道招募，活跃用户更容易进入样本。这是自选样本，并非全市场概率抽样。AI 页面下载因超时未取得全部页面，但以上被引用的完整章节及对应数字均已读取；方法页面完整读取。两页访问日期均为 2026-09-08。

### 2. Agent 团队重视质量、追踪和上线前回归控制

[LangChain State of AI Agents](https://www.langchain.com/stateofaiagents) 对 1,300 多位从业者的调查显示：质量是 Agent 上线的首要障碍，关注度超过成本、安全等其他因素的两倍；小公司受访者中，45.8% 将质量作为首要关注，22.4% 选择成本。报告还称离线评测使用率为 39.8%，在线为 32.5%，并描述大企业用离线评测在用户看到响应之前捕捉回归。

**日期须谨慎：** 当前页面显示“12 June, 2026”，但标题、介绍和正文都明确是 **2024 年调研**，因此这里按 2024 数据使用，不将它冒充 2026 年市场现状。访问日期：2026-09-08。

这是评测产品厂商组织的调查，样本中科技业占 63%，不足以代表所有企业。它能说明所触达 Agent 团队的关注重点，不能证明 Cernora 有未被满足的需求，更不能证明其严格离线证据契约已有采购预算。

### 3. Notion 的价值是发现细分质量问题并快速部署，而非只得到分数

[Braintrust — How Notion evaluates AI at scale across 70 engineers](https://www.braintrust.dev/customers/notion) 引述 Notion AI Modeling Lead Sarah Sachs：70 位工程师围绕评测协作，团队同时跑 regression 和 frontier eval；新模型通过后按适用场景快速部署。案例称能在 24 小时内部署新前沿模型。

具体问题比宏观口号更有参考价值：多语言工作区中 Agent 输出语言不符合预期，团队利用可搜索 trace 找出失败样本，建立专门数据集和评测，并将其保留为回归防线。客户称这对部分 APAC 用户是当年重要的质量改善之一。

这里用户购买的是“找到此前难发现的失败 → 有针对性地修复 → 避免复发”的效率和质量结果。案例没有证明是 Braintrust 单独导致改善，也没有披露对照实验或完整指标。它是**厂商发布、具名客户参与的成功故事**，有选择和归因偏差。页面未见明确发布日期；访问日期：2026-09-08。

### 4. Retool 要求评测结果能改变修复优先级并产生可测提升

[Braintrust — How Retool uses Loop to turn logs into AI roadmap decisions](https://www.braintrust.dev/customers/retool) 引述 Retool AI Engineering Lead Allen Kleiner：生产 trace 太大，人工难以分析；团队用“error rate × usage volume”衡量故障影响，决定修复顺序。

案例中的具体链路包括：Agent 虚报完成，进一步分析发现缺少完成任务所需的 tool definitions，团队在数小时内修复；另一个分类器在分析误分类、建立针对性测试集并逐次评测后，准确率从 72% 到 95%，即增加 **23 个百分点**。不应把页面概览的“23% improvement”当成相对增幅。

它支持“缩短定位时间、把观测转成优先级和干预、验证干预收益”的需求，而且说明现有产品已覆盖这一链条。与 Notion 一样，它是**厂商客户故事**，没有独立效果审计，不能把结果外推到普通团队。Loop 还包含辅助分析功能，因此不能将其收益归因于单纯的评测执行器。页面未见明确发布日期；访问日期：2026-09-08。

## 现成 CI 和测试的替代压力

[Anthropic — Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)，发表于 2026-01-09、访问于 2026-09-08，是模型与 Agent 开发者的工程经验，不是独立市场调查。文章明确指出，编码 Agent 常用 unit tests 验证正确性；SWE-bench 以修复失败测试且不破坏现有测试为通过条件。文章建议用来自真实失败的 20–50 个任务起步，并承认团队可自建框架或直接用简单评测脚本；工具效果取决于任务和 grader 质量。

[Promptfoo 官方 CI/CD 文档源文件](https://github.com/promptfoo/promptfoo/blob/main/site/docs/integrations/ci-cd.md) 已提供批量 eval、GitHub Actions/GitLab/Jenkins 集成、质量阈值、JSON/HTML/JUnit 报告、成本跟踪及自定义结果处理。它还提供 pipeline tags 和 portable exports。核查使用[官方 raw 源文档](https://raw.githubusercontent.com/promptfoo/promptfoo/main/site/docs/integrations/ci-cd.md)，因官网 TLS 连接失败；访问日期：2026-09-08。此处是官方文档声称的能力范围，未执行安装验证。

因此，“能跑测试、比较两个版本、发现回归、生成可携带报告”本身已有明显替代品。普通单仓库编码任务，可以用现有测试、固定版本、CI artifact 和少量脚本解决相当一部分问题。常规 CI 不会自动解决模型随机性、环境隔离、有效证据判定和跨组织独立核验，但这些问题需要先被真实客户确认足够昂贵，才能成为独立产品的理由。

## 对 Cernora 价值命题的含义

- **质量改善：** 公开证据最强。需要把失败证据变成开发者可行动的判断，并验证修复后是否改善真实任务。
- **可靠发布：** 有明确需求，即使一次实验只拦住回归也可能有价值。仍须证明相较已有 CI/eval，Cernora 能多发现重要问题、减少误拦截，或更快完成决策。
- **降低成本：** 调研确认有人关注，现有工具已可测成本；本轮材料未获得 Cernora 类独立证据层带来实际节省的直接客户证据。应以“相同质量下每个成功任务成本”验证，不能仅比较 token 数。
- **合规、跨系统离线证据：** 属于可验证的细分假设。本轮未找到足够的独立需求证据，证明客户愿为严格离线重建、完整性契约单独购买。普通导出、私有部署也可能已满足用户；不能把自身工程优势当成市场缺口。

## 当前评测方向与需求证据的对应

Cernora 的产品目标仍是帮助用户依据证据定位问题、验证干预、控制回归和成本。
当前先验证一个可确定性评分的切片：Agent 是否正确消费工具返回的事实，识别对象关系，
保留缺失信息，并按约定输出有证据引用的结构化答案。Agent 的运行由外部工作流承担，
Cernora 评测完成态导出；暂不把多步规划、领域判断或完整任务效用纳入这一个切片。

| 需要回答的问题 | 当前切片能提供的证据 | 仍需补齐的证据 |
| --- | --- | --- |
| 是否正确使用返回事实？ | 字段值、对象关系、完整性、缺失说明及引用的确定性检查 | 任务参考的独立校准，以及不同任务分布下的适用性。 |
| 是否帮助改善 Agent？ | 失败样本可以形成具体干预假设，例如输出契约不符合要求 | 固定条件下的单变量对照、未参与调优案例的独立验证、回归与成本约束。 |
| 是否改善真实工作结果？ | 结构化答案是某些后续任务的必要输入 | 使用方确认的任务效用、人工返工或决策时间变化；格式正确本身不足以证明。 |
| 是否有成本价值？ | 有可靠导出时记录调用、token、耗时及重复请求 | 同等质量下每个成功任务成本，包括接入、人工审核和维护成本。 |
| 是否值得采用独立评测核心？ | 完成态证据可复核，运行与评分职责分离 | 与现有流程比较的额外价值、持续采用和付费意愿。 |

中立 Adapter 示例、首次接入教程与独立安装验收证明接入路径可用，不等于完成客户采用
验证。`inspect` 成功也不等于 Profile 评测通过；完整证据链需要导入、评分与严格重载。
开发评测已跑通，但独立人工参考、确认性基线及干预收益尚未完成验证。不能把“有分数”
“格式符合率提高”或“可复核”直接写成用户价值已经成立。

脱敏和任务简化产生独立的数据版本。它们适合验证限定机制，但改变文本分布、长度或
任务内容后，不能直接把结果外推到原始任务。关联案例需按组划分，重复运行不增加独立
业务样本数；源事实核对不能冒充独立人工校准。

当前先完成这一有界验证，再进入 Chora 的一类完成态任务。Metric SDK、通用 Runtime
Connector 和通用 Judge 由重复出现的真实需求触发；本切片可确定性评分，不因市场上已有
Judge 产品而加入在线评分依赖。具体交付状态和顺序只在路线图维护，本文保留需求假设
与证据强弱判断。

## 可证伪的产品验证建议

以下是后续产品价值验证建议，不是当前开发评测已完成的事项，也不作为 Preview 交付的
新增前置条件。样本内技术改进和客户价值验证分别验收。

选择 3 个有实际 Agent 发布流程、愿意提供真实失败案例的设计伙伴，明确其当前工具栈，并在事先限定的 2–4 周验证期中与其原流程比较。以下数字只是初始验证门槛建议，不是行业标准，应在开始前按任务成本冻结：

1. **帮助改好：** 至少一个真实 Agent，Cernora 的证据直接指导具体干预，在新的冻结留出任务上达到预声明的业务提升目标；同时满足质量、安全及成本约束。记录“哪个发现导致哪项改动”，避免把本来就会发生的改进归功于工具。
2. **帮助更快决定：** 对可比问题，定位到可验证根因或作出发布决定的工程师用时中位数降低至少 30%，统计接入、看报告和维护评测的成本。不能仅统计机器执行时间。
3. **证明与替代品的差异：** 用客户现有 CI/eval 的同一批案例，发现至少一个经客户确认有影响、现有流程遗漏的问题；同时记录误报和无法判断，不能只展示命中案例。
4. **验证采用，而非礼貌反馈：** 至少 2 个伙伴主动用于下一次真实任务迭代，并愿投入集成时间或付费试点。对于离线证据定位，必须由负责验收/安全/采购的接收方独立使用证据完成一次真实决策。

如果工具只得到“设计很严谨”的评价，客户却仍靠原工具完成定位、修复和发布，且不继续使用，应判定当前产品定位未获验证。届时应缩小为可嵌入现有平台的协议/SDK，或调整用户问题，而不是继续扩大功能清单。
